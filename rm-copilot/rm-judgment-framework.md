# RM 销售经理 Copilot・判断框架（M0 草案）

> ⚠️ **已被 `V0-CONTRACT.md` 取代（2026-09-12）**。本文档仅作过程存档，判断链路以 V0 合同为准。
> 状态：M0 业务建模产物，待 RM 验收调整。
> 定位：MVP = 验证「已知信息 → 具体行动建议」的逻辑成立，并能持续经营客户。
> 原则：AI 负责基于已知信息给出建议；现实商业判断（报价、折扣、资源投入、最终立项）归 RM。



***

## 1. 产品边界（MVP 定义）

### 负责



* 从已知信息中识别客户**最值得优先验证的痛点 / 场景**（唯一主方向）；

* 输出**问题价值陈述（Before/After）**：把痛点翻译成高层语言（钱 / 效率 / 风险 / 竞争力），用于高层对话；

* 匹配**飞书方案**（基于方案素材库，标注 "截至素材版本"）；

* 输出**具体行动建议**：找谁、聊什么、要什么承诺、继续 / 停止条件；

* 通过 **Decision Card 回写**保持同一客户的判断连续性（保持 / 重判 / 暂缓 / 停止）。

### 不负责（MVP 不做，RM 判断）



* 续费判断（续约时间线、续费金额、续约风险信号）；

* 报价、折扣、商务条款；

* 是否投入售前 / 产品 / 研发资源；

* 最终是否立项、承诺与商业推进。

### AI 与 RM 分工



| 层              | 负责方               | 说明             |
| -------------- | ----------------- | -------------- |
| 客户侧方向（痛点 / 场景） | **AI 推荐**         | 依据 + 反证 + 最大未知 |
| 方案匹配           | **AI 建议 + RM 确认** | 方案信息截至素材版本     |
| 商业判断           | **RM 决定**         | 报价、资源、立项       |
| 状态写入           | **RM 确认后 AI 写入**  | 草案 → 确认 → 写入   |

## 2. 输入层：已知信息变量

进入判断的输入分为五类，缺少哪类在输出中明确标注 "未知 / 待补"，不猜测：



| 类别   | 变量                                                    | 示例                      |
| ---- | ----------------------------------------------------- | ----------------------- |
| 客户组织 | 行业、员工规模、组织复杂度、IT / 数字化阶段                              | 跨境电商，500 人，多分公司，数字化中早期  |
| 飞书使用 | 已启用模块、各模块活跃度（高 / 中 / 低 / 未用）、用量趋势（上升 / 平稳 / 下滑）、覆盖部门数 | 文档 + IM 高频，审批低频，多维表格未启用 |
| 客户表达 | 近期需求、痛点、反馈、投诉                                         | 跨部门数据协作乱，希望统一报表         |
| 历史互动 | 上一次互动结论、已有方案、关键人关系                                    | 上次已推文档方案，业务负责人认可        |
| 公开研究 | 行业动态、客户公开信息（联网核验）                                     | 行业在推门店数字化               |

**证据分层**：客户输入 > 公开事实 > 推断 > 待验证假设。输出中必须区分。

## 3. 判断层：唯一主方向

### 候选方向从哪来



1. **客户明确表达的需求 / 痛点**（最高优先级）；

2. **使用数据暴露的缺口**（模块未启用 / 活跃下滑 / 覆盖部门少 + 相邻业务场景）；

3. **行业常见痛点**但客户未表达（需验证，降级为验证动作，不直接推方案）。

### 收敛规则



* 每轮只保留**一个主方向**，其余进候选池（只记名称、暂不推进原因、重启条件，不附行动）；

* 输出结构：主方向 + 问题价值陈述（Before/After）+ 关键依据 + 重要反证 + 当前最大未知；

* 证据不足但值得继续时，主方向写成**窄范围验证动作**，不凑方案；

* 价值门槛未过（客户不认可痛点 / 无推动人 / 客户自己感知不到价值）→ 建议暂缓或停止。

### 价值传递：输出给高层的问题价值

**原则：商业化的起点不是方案，是问题价值。** 一个方向成立的标志不是 "我觉得客户需要"，而是 "客户自己也觉得需要"。因此每个主方向都附带价值传递素材：

#### 问题价值陈述（Before / After）



| 视角         | 内容            | 语言要求                                     |
| ---------- | ------------- | ---------------------------------------- |
| Before（现状） | 客户当前状态 + 具体代价 | 用客户自己的业务事实；可量化（时间 / 成本 / 效率 / 风险 / 机会损失） |
| After（改变后） | 变化后的可感知收益     | 高层业务语言：收入 / 成本 / 效率 / 风险 / 组织能力 / 竞争力    |

**价值主张（一句话）**：痛点 → 收益的因果链。例："因为数据靠人工整理、报表慢两周，所以决策滞后；如果打通数据流，决策从拍脑袋变成看数据。"

#### 高层对话素材（一页纸）



1. **问题价值**：高层关心的语言 —— 这件事不解决，客户损失什么；解决了，得到什么；

2. **为什么现在**：紧迫性（行业趋势 / 风险窗口 / 已有资源）；

3. **下一步**：轻承诺 —— 一次验证动作，不是方案推销。

#### 客户共鸣验证设计（让客户自己说 "需要"）



* "聊什么" 不直接断言客户痛点，而是**设计验证性提问**，让客户自己确认或否认；

* 区分两类问题：


  * **证据支持的问题**（客户表达过 / 数据支持）→ 可较直接陈述；

  * **假设的问题**（推断 / 行业通病）→ 必须设计成开放提问，客户确认后才升级为 "已共鸣的问题"；

* 价值主张只有在客户共鸣验证通过后才算成立；在此之前标记为 "待验证价值"。

### 与 JD 职责的对应（MVP 覆盖部分）



| JD 职责                    | MVP 中对应           |
| ------------------------ | ----------------- |
| 1 续约率 / 续费 / 增购          | 不做（MVP 裁剪）        |
| 2 CEO 沟通 / 重点客户维护 / 挖掘增购 | 决策链识别 + 找对人（部分覆盖） |
| 3 专业咨询、解决疑问              | 痛点验证与咨询议题（覆盖）     |
| 4 对接需求、与产品团队协作优化方案       | 痛点 → 方案匹配（覆盖）     |
| 5 成功经验规模化复制              | MVP 后置（候选方向之一）    |

## 4. 方案匹配层：痛点 / 场景 → 飞书方案

输入：判断层的主方向（痛点 / 场景）。

数据源：方案素材库（用户提供的飞书方案文档 / PDF，M2 落地）。

匹配度分级：



| 级别   | 定义              | 行动含义                 |
| ---- | --------------- | -------------------- |
| 直接匹配 | 素材库有方案直接对应痛点    | 行动建议直接引用方案           |
| 部分匹配 | 方案覆盖部分痛点，需组合或定制 | 行动建议引用方案 + 标注需确认的差距  |
| 无匹配  | 素材库无对应方案        | 不强行推方案，行动改为「验证需求真实性」 |

约束：



* 所有方案引用标注**来源 + 版本日期**（截至素材版本）；

* 方案信息不足以支撑判断时，明确 "素材库未覆盖"，不编造方案能力。



***

## 5. 行动层：下一次客户互动怎么开



| 字段    | 规则                                                |
| ----- | ------------------------------------------------- |
| 找谁    | 决策链上**能推动该场景**的人（业务负责人 / IT 负责人 / 高层），不默认 CEO     |
| 聊什么   | 首要议题只聊一个：用验证性提问让客户自己确认痛点（共鸣）→ 再展示 Before/After 价值 |
| 要什么承诺 | 客户侧行动：提供使用数据 / 安排相关人员 / 同意试点某模块                   |
| 继续条件  | 客户给出明确进展信号（认可痛点、安排人、同意试点）                         |
| 停止条件  | 客户否认痛点 / 方案不匹配 / 找不到推动人                           |

## 6. 状态回写：持续经营客户

### Decision Card 结构（CSM 版 + 价值传递扩展）



```
\## 当前 Decision Card

\- 状态：待确认 / 推进中 / 暂缓 / 已停止

\- 当前唯一主方向：

\- 问题价值（Before → After）：

&#x20; \- Before（现状代价）：

&#x20; \- After（改变后收益）：

&#x20; \- 价值主张（一句话）：

\- 当前判断：

\- 关键依据：

\- 重要反证：

\- 当前最大未知：

\- 匹配飞书方案：

\- 下一步找谁：

\- 聊什么（含共鸣验证提问）：

\- 希望客户采取的实际行动：

\- 继续条件：

\- 停止条件：
```

### 更新机制



* 草案 → RM 确认 → 写入客户状态文件；

* 新反馈触发：保持 / 重判 / 暂缓 / 停止；

* 保留已否定结论（除非新证据满足重启条件）；

* 同一客户的判断跨轮次不 "失忆"。

## 7. 测试账户基线（合成示例数据，用于回归）

> 以下为 M0 阶段手工编写的期望判断，M1 跑通后作为回归基线。数据为合成示例。

### 账户 A：某跨境电商（典型增购场景）



* **已知信息**：跨境电商，300 人；文档 + IM 高频、多维表格未启用、审批低频；客户反馈 "跨部门数据协作乱，报表靠人工"；运营负责人是推动人。

* **期望主方向**：多维表格 + 审批的数据协作场景（客户明确表达，优先级最高）。

* **期望价值（Before/After）**：Before—— 跨部门报表靠人工，月报 2 周才出，决策靠经验；After—— 数据自动汇总，报表实时，管理层看数据决策。价值主张："把决策从 ' 拍脑袋 ' 变成 ' 看数据 '"。

* **期望行动**：找运营负责人 → 先用验证性提问确认 "报表周期与决策滞后" 的代价 → 再展示方案 → 要承诺：提供一份现有报表样例 + 安排 1 次演示。

### 账户 B：某制造企业（使用缺口验证）



* **已知信息**：制造企业，800 人；全模块已启用但活跃度普遍下滑；IT 负责人刚更替；客户未表达明确需求。

* **期望主方向**：使用缺口原因验证（窄范围验证动作，不直接推方案）。

* **期望价值（Before/After）**：Before—— 全员启用但活跃下滑，数字化投入回报存疑，新 IT 负责人上任即面临 "这套系统值不值" 的质询；After—— 使用深度回升，投入可见回报。价值主张："让数字化投入从 ' 花了钱 ' 变成 ' 看得见回报 '"。

* **期望行动**：找新 IT 负责人 → 用开放提问了解各部门使用阻力（不预设结论）→ 要承诺：提供近一季度模块使用数据。

### 账户 C：某互联网公司（方案扩展）



* **已知信息**：互联网公司，1500 人；OKR 模块使用良好；客户主动问 "目标管理能否扩展到子公司"；高层关注。

* **期望主方向**：OKR 向子公司扩展（客户明确表达 + 方案可匹配）。

* **期望价值（Before/After）**：Before—— 子公司目标靠线下表格，集团对齐靠开会，战略落地慢；After—— 目标跨公司对齐，OKR 从总部复制到子公司，战略节奏一致。价值主张："让集团战略从 ' 总部知道 ' 变成 ' 全公司对齐 '"。

* **期望行动**：找 CEO 或 HR 负责人 → 用提问确认 "子公司目标对齐的代价" → 聊扩展范围与试点方式 → 要承诺：明确试点子公司范围 + 安排一次高层对齐会。

### 回归基线用法



* 每个账户记录：输入摘要 → 期望主方向 → 期望价值（Before/After）→ 期望行动；

* M1/M2 改动规则后，重跑三个账户，检查输出是否与期望一致（方向保持、不跳方向、价值陈述不脱离客户事实、不推无关方案）。
